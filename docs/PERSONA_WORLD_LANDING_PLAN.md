## 1. 世界模型（双层 + 意图路由 + 选用）

```
登录（=人物激活）
   │
   ▼
【第一层 · 人本世界 Persona World】（门户）
   一张以人为本的「生活全景」：居所/餐饮/学习/工作/社交/出行·旅游/健康 …
   人在这里用「思想与行为」表达意向（我饿了 / 我想学 / 我要出门）
   │  选择一个意向  →  意图路由（WorldRouter）
   ▼
【第二层 · 模块内容世界 Module World】（各模块内）
   模块用自己的「活动场景」承载功能全过程：
     订餐  → 选店 → 点菜 → 下单 → 支付 → 取餐
     智学慧眼 → 选学科 → 知识营地（学科登顶） → 测评 → 复盘
   │
   ▼
【贯穿两层 · 人物孪生 PersonTwin】（人本体，只读装配）
   六面：身份 / 状态 / 世界 / 经历 / 记忆 / 关系 —— 跨模块汇总，回到人本世界看自己
```

**三条规则**：
1. **人本世界只放"生活主题"**（人为什么做），**不放模块功能**（怎么做）——功能一律在第二层。
2. **模块入口 = 意向**，不是"应用图标"；"申请/启用模块"复用既有 **`user_module` 选用**（opt-in）+ **`app_module` 角色可见性**（授权）。
3. **孪生不重复存状态**（沿用 `student-twin` 红线）：profile 取 identity、state 取业务聚合、world 取场景、events 取 `twin.event`、memories 取 `agent.memory`。

## 2. 本体/数据模型（结构变更只改 YAML → codegen → 迁移）

**演进既有 `student-twin.ontology.yaml` → 新增 `person-twin.ontology.yaml`**（人本体泛化）：

| 对象 | 表 | 说明 |
|---|---|---|
| `Person` | `public.users`(abstract) | 人本体锚点（**所有登录人**） |
| `LifeScene` | `ontology.life_scene` | **人本世界场景闭集**（生活主题：居所/餐饮/学习/工作/社交/出行旅游/健康…）字段：code/name/en/theme(衣·食·住·行·工作·生活·旅游)/icon/pos(x,y)/order |
| `LifeIntent` | `ontology.life_intent` | **场景内意向**（我饿了/我想学/我要出门…）：sceneId、label、desc、actionIds |
| `SceneModuleLink` | `ontology.scene_module_link` | **意向/场景 ↔ 模块**映射：sceneId/intentId → `app_module.code`（含是否需申请 opt-in） |
| `ModuleScene` | `ontology.module_scene` | **模块内容世界场景**（模块内活动节点）：moduleCode、code、name、order、actId |
| `TwinEvent` | `twin.event`（既有，kind 闭集扩展） | 经历（append-only）：kind 增加 `intent`/`module`/`world` |
| `PersonTwin` | —（描述符） | 六面：profile/state/world(**LifeScene**)/events/memories/relations |

> 全部走 **本体驱动**：改 YAML → `@gri/codegen` → 迁移；**禁手写结构 DDL**。原型 `ONTOLOGY_YAML` 已给出可直接对齐的 DSL 形态（`Place`→`LifeScene`、`ActionDef`→`LifeIntent`）。

**API（`services/api/src/modules/twin` 扩展）**：
- `GET /api/twin/me`（六面总览，world 返回人本世界场景）
- `GET /api/twin/world`（人本世界：场景 + 意向 + 场景↔模块）
- `POST /api/twin/intent`（记录一次意向 → 路由到模块；写 `TwinEvent(kind=intent)`）
- `GET /api/module-scene/:moduleCode`（模块内容世界场景，供第二层）
- 既有 `/me/events`、`/me/action`、`/me/profile`、`/me/replay`、`/me/export|import` 复用。

## 3. 门户「人本世界」（工作台并入）

登录成功 → **人物首页 = 人本世界**（不再是模块卡列表）：
- **人物卡**（孪生六面之 profile/state：头像、角色、精力/经历/等级、当前所在场景）。
- **生活全景图（2D/SVG）**：生活主题场景的拟真地图；人物有"当前位置"；点场景进入主题。
- **场景内 → 意向**：进入"餐饮"，看到"我想吃饭/订个午饭/看看附近"，点意向 → 打开/申请 `food`。
- **未开放场景**：以"建设中"占位（保留世界完整感）。
- **我的模块**（原工作台的"已选用插件"）：并入世界，表现为"我常去的地方/我的家当"，而不是卡片列表。

**模块可见性**：仍走 `app_module.allowed_roles`（授权，服务端强制）+ `user_module`（选用，opt-in）；**人本世界只呈现"你能用的"**。

## 4. 模块内容世界（第二层）

- **统一"世界语言"**：每个模块内用同一套场景/节点/路径视觉（复用 `twin/world.vue` 的地图——放大/营地/路径）。
- **智学慧眼**：内容世界 = 学科版图（**学科登顶**就在这）——选学科 → 知识营地 → 登顶/测评/复盘。**UI/功能待完善（另立卡）**。
- **订餐**：内容世界 = "店内"活动链（选店→点菜→下单→支付→取餐），2D/SVG 场景。
- **组织/看板**：内容世界 = "办公室/经营指挥台"场景。
- **过渡**：门户→模块用**统一过场**（同色系/同拟真风 + SSO 免二登），让"进入不同模块"像"走进不同街区"。

## 5. 2D/SVG 视觉方向（拟真，不 3D）

- **风格**：矢量**等距（isometric）/写实描摹**插画；统一色板与光照（GRI 令牌）；避开"卡通扁平"。
- **拟真手法**：透视/等距网格、材质分层（地面/建筑/植被/水面）、软阴影、景深色调、昼夜/天气氛围（可选）。
- **交互拟真**：人物头像在地图上"移动"（CSS/SVG 补间）；进入场景有"推近/开门"式过渡；场景内有可点物件（招牌/桌椅/书本）。
- **性能**：SVG 分层 + 按需渲染（可复用 `apps/explorer` 的几何精简经验）；避免一次性渲染全城超大树。
- **原型对照**：`人物数字孪生系统_C1.html` 的虚拟城市即 SVG——**在同一实现路线上做精**（目前偏示意图，拟真度要上一档）。

**视觉验收基线（避免扯皮）**：人物世界与模块场景**看起来是同一个"世界"**（同色同光同透视），场景可辨识生活主题、有"地点感"，人物有位置与移动；**不要求**自由行走/物理/3D。

## 7. 可达性评估 + 需你确认（关键：先对齐期望，免得返工）

**能达到的**：双层世界、意图路由、人本世界拟真 SVG、工作台并入、学科登顶归位、孪生跨模块汇总 —— **均可达**。

**必须和你确认的 4 点（影响成本/期望）**：

1. **"像进入现实世界"的层次**：SVG 可做**强插画拟真**（等距全景、有人物移动、有场景过渡），但**不是可自由行走/可 3D 环视**。请确认接受**"拟真插画全景"**这一档（否则需 3D，量级完全不同）。
2. **跨应用的"一个世界"是剪接还是无缝**：人本世界在**门户**（uni-app），模块内容世界在**各模块 app**（uni-app，编译产物、运行时不能加载外部模块）。所以"走进模块"是**一次同风格的过场 + 跳转**（SSO 免二登），**不是同一张地图无缝走出**。确认接受这种"**过关式**"连续感？
3. **模块内容世界逐模块定制**：每个模块的"内容世界"是**单独设计+实现**的工作（成本线性）。建议**先 2 个**（智学慧眼/订餐）+ 其余"建设中"占位。确认这个推进节奏？
4. **人物身份与"人本世界"边界的例外**：运营类模块（组织管理台/统计/身份中心/看板）是**工作职能**，不完全属于"个人生活主题"。它们在人本世界里怎么摆——**放进"工作"场景**，还是**保留一个"运营后台"独立入口**（不走世界）？

**另外先声明两处"做不到/要另算"的点**：
- **运行时插件化**：uni-app 编译产物**无法**像桌面端那样"装一个模块=装一个场景包"。世界是**入口/外壳**，模块功能仍在各自页面内实现。
- **学科登顶**：现状 UI/功能你已指出待完善 → 它是 **W4 独立卡**，不在 W1–W3 里夹带。

## 9. v2.1 增补：4 点答复已定 + 社会组织层（组织本体 + 激活物化）

### 9.1 已定（用户 2026-10-15 答复）
1. **先不做 3D** —— 视觉基线 = 2D/SVG 拟真插画。
2. **采用「过关式」连续** —— 门户→模块：同风格过场 + 跳转（SSO 免二登）。
3. **推进节奏** —— 先 1 人本世界 + 2 个模块内容世界（智学慧眼 / 订餐）+ 其余"建设中"占位。
4. **保留「运营后台」独立入口**（组织管理台/统计/身份中心/看板 不走人本世界；组织管理尤其重要）。

### 9.2 新增维度：社会组织本体（人本论的社会层）
用户表述（助手复述）：
- 社会由**组织**构成（**家庭 / 学校 / 单位** …）= **人的存在基础**；
- 人挂在**一个或多个组织**下（**多归属**）；
- **每个组织也是本体、可被实例化**（组织类型 → 具体实例）；
- **人激活（登录）后**，其**所有属性 + 关联组织**物化进**内存（Redis 会话）**，供各模块**实时引用与展示**。

**设计落点**：
- **本体**：新增 `organization.ontology.yaml` —— Object `Organization`（`type` 闭集：family/school/company/department/community/…；自引用 parent；可实例化）、Object `OrgMember`（person↔org；role/status/department/title）；`Person` 经 `OrgMember` **多对多**。
  （现状：`tenant.organizations` 已有 `type/parent_id/parent_path/level/settings/metadata`，`tenant.organization_members` 已有 `role/status/department/title` —— **结构已具备，缺本体化**。）
- **组织进人本世界**：家=家庭组织、学校=学校组织、单位=单位组织——**组织也是世界的"地点"**。
- **激活物化（Session Context）**：登录 → 组装 `{person profile, orgs[], roles[], twin 快照}` → 存 **Redis**（key=userId/sessionId；TTL + 变更失效）；各端读上下文，免重复拼装。
  （现状：`services/api` 未见 Redis 使用——需新增。）
- **红线**：Redis 是**缓存 / 物化视图**，**不是授权真源**——鉴权仍走服务端 RBAC（`app_module.allowed_roles` + 组织角色）；上下文只加速"展示与引用"，不替代鉴权。

### 9.3 待确认（社会组织层）
1. **组织类型闭集**：family/school/company/department/community/… 的**具体清单**？
2. **"可实例化"的含义**：类型是**枚举**还是独立本体 `OrganizationType`？组织实例是否也有**自己的状态/孪生**（"组织孪生"）？
3. **多归属**：是否需要"**主组织 / 当前组织**"与**切换**（可复用工作台已有的作用域选择器）？
4. **会话物化**：存什么**粒度**、**失效策略**（组织/角色变更、登出）、Redis 是否持久（还是纯缓存）？
5. **组织可视**：组织是否要在**人本世界里可视**（如"我的家 / 我的学校 / 我的单位"作为场景）？

## 10. v2.2：社会组织层已定（用户 2026-10-15 答复）

### 10.1 已定（用户答复）
1. **组织类型 = 现实社会组织形式**（家庭 / 学校 / 单位 / 社会团体…凡能承载人的都算）；**运营后台维护组织类型**；通常**注册人自建自己的组织**；**必要时需资质**（家庭户口本验真 / 学校·单位执照 + 单位盖章 + 法人签字）。
2. **组织是独立本体**，与"人本体"同级——现实真实事物的虚拟映射 = **组织本体的个体数字孪生（组织孪生）**。
3. **无主组织**：组织是人的**关联属性 / 活动标签**（一人多组织，彼此平等）。
4. **失效**：变更通过后**直接更新**最好；若活动/会话已用旧信息无法同步 → **提示重新登录**亦可接受。**Redis 只做缓存、不持久化**。诉求：激活后"人与直接属性/关联（组织、角色权限）都在内存随时可取"。
5. 组织在**人本世界**里体现为**主要静态信息入口卡** → **跳转组织孪生页**（组织孪生独立、内容丰富，如人的孪生体）。

### 10.2 设计落点
- **本体**：新增 `organization.ontology.yaml`
  - `Organization`（独立本体，可实例化）：name / type → `OrganizationType` / code / 资质 / logo / desc / 自引用 parent。
  - `OrganizationType`（**独立本体**，运营后台维护；类型可增）。
  - `OrgMember`（`Person` ↔ `Organization` **多对多**；role / tags / status）。
  - `OrgTwin`（**组织孪生**，六面）：profile（身份/类型/资质/静态信息）· state（状态/规模/等级）· world（子组织/部门/场所）· events（组织经历 append-only）· memories（公告/档案）· relations（与其他组织/人的关系）+ members（成员）。
  - `MembershipVerification`（资质/验真：类型、材料、状态、审核人）—— **可分期**。
- **人本世界**：组织 → **入口卡**（静态摘要）→ 组织孪生页。
- **激活物化（Session Context，回答"Redis 怎么用最值"）**：
  - 登录 → 组装 `ctx:user:<id>` = `{version, profile, orgs:[{id,name,type,role,tags}], permissions, twinSnapshot}`（Redis Hash/String；TTL 滑动续期 ~30min）。
  - 各模块请求 → 读 Redis（亚毫秒），**不再查库拼装**；跨 API 副本共享。
  - **变更即失效**：组织/角色审批通过 → 写穿更新该 key（+ Pub/Sub 广播，多副本一致）。
  - **版本号(etag)**：页面/模块发现版本变了 → 提示"组织信息已更新，请重新登录"（覆盖"活动过程中用旧信息无法同步"）。
  - **红线**：Redis = 内存里的当下真相**缓存**；权威真源仍是 DB；敏感写仍服务端校验；**不持久化**（符合你的要求）。
  - 现状：`gri-redis` 可用（PONG），但 `services/api` **未接 Redis**（无 REDIS env）→ 需新增。

### 10.3 待确认（组织层）
1. **资质验证的时点**：本期就要（材料上传 + 审核流 + 验真），还是**先做"组织自建 + 类型维护"**、资质审核列为后续期？
2. **组织孪生的内容范围**："world（子组织）"是否就是组织树（部门/子组织）？组织"经历/记忆"从哪些行为采集（成员活动聚合？）？
3. **权限口径**：组织角色（`tenant.organization_roles` 现为**空表**）本期是否启用？还是先用组织内 owner/admin/member 简档？
