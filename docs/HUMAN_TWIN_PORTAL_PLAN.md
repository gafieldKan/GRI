# 人物数字孪生 → 登录入口 与「虚拟世界」模块化：3 个角度的实现方案

> 状态：设计分析 v1 ｜ 2026-10-15 ｜ 作者：总负责人（助手）
> 输入：用户愿景 + 原型 `人物数字孪生系统_C1.html`（PERSONA · 人物数字孪生系统 C1）
> 前置实测：见 §1；项目现状：见 §2。

---

## 1. 原型分析（PERSONA C1，实测）

**形态**：单文件自包含 HTML（852 行 / 145KB），**纯 SVG 渲染**（无 three.js/WebGL/canvas；`grep THREE/canvas = 0`）。含登录态、左侧导航、顶栏、主区、右侧明细。

**信息架构（7 视图）**：`孪生总览 / 人物画像 / 虚拟世界 / 本体孪生 / 行为与记忆 / 状态回放 / 数据与设置`。

**登录即"唤醒"**：登录页文案「唤醒你的孪生体 · 离线可用 · 账号独立档案 · 登录恢复状态」——**账号=人物档案，登录=孪生激活，状态/记忆/上次位置恢复**。这正是用户说的"账号成功登录后，代表人物被激活"。

**数据模型（关键：已是本体驱动）**：原型内嵌一份数字化 ontology DSL，**与 GRI `packages/ontology/ontologies/*.ontology.yaml` 同构**：
- Objects：`Person`(abstract 锚点) · `Place`(世界场景闭集) · `ActionDef`(行动闭集) · `TwinEvent`(append-only) · `Memory` · `Relation`
- Twin：`PersonaTwin`（entity=Person，world=Place，**六面** profile/state/world/events/memories/relations + **13 个动词闭集**）
- 编译期 `buildOntologyDescriptor()`（DSL→描述符，确定性可测）；运行期 `assembleTwin()`（描述符→实时装配，只读）；`ontologyChecks()`（DSL ↔ 运行时**防漂移自检**）。
- **"世界" = 6 个生活场景**（孪生公寓/知识学院/协作工坊/社交广场/城市公园/创意展馆），每场景挂 2 个行动；行动结算 精力/时长/经历(XP)/积分/能力(5 维)/关系(bond)。地图为 SVG 虚拟城市，含人物当前位置。
- 红线（原型自述）：本体页只读、浏览不产事件、结构变更只改 DSL。

**结论**：原型不是玩具，是**"人本论 + 本体→孪生 + 虚拟世界"**的完整设计语言，且与 GRI 既有机制同构——**可作为 GRI 人物孪生的设计蓝本直接对齐**。

## 2. 项目现状（实测，勿凭印象）

- **已有孪生本体**：`packages/ontology/ontologies/student-twin.ontology.yaml`（`StudentTwin`：entity=**User**，world=**KnowledgeArea**，六面同原型；动词 lesson/practice/review/chat/exam/rest）。→ 孪生机制**已存在**，但**是"学生 × 学科"垂直**，不是"人 × 生活世界"。
- **后端**：`services/api/src/modules/twin/*` —— `GET /api/twin/me`、`/me/events`、`POST /me/action`、`/me/profile`、`/me/backfill`、`GET /me/replay`、`/me/export`、`POST /me/import`。`assembleOverview(entityId, subject='math')` —— **world 按学科取版图**（`CurriculumService.knowledgeMap`）。
- **前端孪生**：`apps/web-ai-tutor/src/pages/twin/`（world **1174 行** + profile/memory/replay/data）—— **孪生现在就长在「智学慧眼」里**。
- **学科登顶**：**就在 `twin/world.vue`**（"虚拟世界 · 登峰：每门学科都是一座山——每个知识域是一个营地；已登顶营地"）。→ 用户要保留的正是这个**学科版图/登顶视图**。
- **门户**：`apps/portal` = SSO 统一入口 + 工作台（`pages/workbench`，模块卡目录）。已有 `app-module` 注册表本体（`AppModule` + 角色可见性 + `UserModule` 选用 + `ModuleRegion/Industry` 可选维度）。
- **平台方向（已裁决）**：用户选 **A 务实门户**（`docs/PLATFORM_DIRECTION_OPTIONS.md`）；**不做多租户**；前端为 **uni-app 编译产物**（**无运行时插件能力**，真"微前端"是大工程）。
- **已有 SSO**：`auth-center`(RS256) + `@gri/auth-client`（三端共享会话 `gri-auth-token`）。

**核心张力**：孪生现在**绑在"学生×学科"**且**长在智学慧眼**；用户要它**上移到登录入口**、**以"人"为本**、**模块=虚拟世界场景**，同时**学科登顶留在智学慧眼**。

## 3. 三个角度的方案

### 方案 A —— 产品/体验角度：**「门户即人物世界」**（门户升级为 Persona Home，模块=世界场景）

- 登录成功 → 门户进入「**人物孪生首页**」（复刻原型 7 视图：孪生总览/人物画像/**虚拟世界**/本体孪生/行为与记忆/状态回放/数据与设置）。
- 「**虚拟世界**」的世界 = **人本世界（Place 闭集）**，每个场景 = **一个模块入口**：知识学院→智学慧眼 · 协作工坊→组织/协作 · 社交广场/创意展馆/城市公园→对应模块或预留。
- **智学慧眼保留为「知识学院」场景**，其内部**仍有「学科登顶」版图视图**（不迁走，原位保留）。
- 后端：twin 服务**泛化 world**：`KnowledgeArea` → `Place` 闭集 + 场景↔`AppModule` 映射；孪生"人本体"从 `User`（学生）泛化。
- **利**：最贴愿景（登录即人物、模块=场景）；本体驱动一致（原型 DSL 已在）；学科登顶原位保留；SSO/注册表可复用。
- **弊**：门户要从"工作台"**重写成孪生外壳**；world 模型泛化（Place + 场景↔模块映射，需本体扩展）；跨 app（portal + web-ai-tutor + web）场景化设计量大。
- **适合**：以终态为目标、愿意一次把体验做对。

### 方案 B —— 平台/架构角度：**「孪生中台 + 本体驱动场景」**（Twin 升为平台域，多前端消费）

- 把 twin 独立为**平台级域**：人本体 = `public.users`，world = `Place` 闭集；门户/智学慧眼/订餐/组织**都消费同一孪生运行时 API**（六面统一）。
- 「**场景 ↔ 模块**」由**本体声明**（`Place` ↔ `AppModule` 关联），沿用已有 `app-module` 注册表（角色可见性 + 用户选用 + 维度限定）。
- 智学慧眼是**其中一个模块（场景）**；学科登顶是其模块内视图。
- 前端：各端只做"**世界皮肤**"；门户提供统一世界外壳。
- **利**：一次孪生、处处消费；与既有本体驱动/注册表/SSO 高度契合；可**渐进**（先门户 + 智学慧眼）。
- **弊**：**改动面最大**（twin 域重定义 + 多端接入 + 权限/治理边界重画）；周期最长；须先泛化"人本体"（非学生场景，如教师/商家/组织成员是否也有孪生？）。
- **适合**：想做成"平台底座"、长期多模块复用。

### 方案 C —— 工程/交付角度：**「虚拟世界外壳 + 模块内嵌」**（最小改动，先出效果）

- 登录后进入「**虚拟世界外壳**」（门户升级为地图/场景外壳），世界里点开某场景 = **内嵌对应模块页面**（经既有 SSO **免二次登录**）。
- 学科登顶**仍在智学慧眼内部**（作为"知识学院"场景点开后的页面）。
- **利**：**最快见效**、风险低（复用现有 app + SSO + 场景↔模块映射）；可先行验证"虚拟世界入口"体验。
- **弊**：世界与模块是"**壳 + 嵌入**"两层皮（**非深度融合**）；多技术栈（uni-app SPA）混嵌的长期维护成本；与"用虚拟世界表现方式实现模块功能"的**终态有差距**（本质是入口，不是重构）。
- **适合**：先验证体验、快速给用户一个能点的东西。

## 4. 推荐：**A 为终态方向 · C 的手法是第一步 · B 的边界先立住**

**分三段走（不推倒重来）**：

1. **第一步（C 的手法，A 的皮）**：登录成功 → 门户「**人物首页**」（=工作台升级：人物卡 + **虚拟世界地图**，场景=模块入口）。世界上点场景 → 现有模块页（SSO 直达）。**学科登顶仍归智学慧眼**。→ 最快让用户"亲手点"到"登录即人物、模块=场景"。
2. **第二步（A 的内核）**：把 twin 的 **world 泛化为 Place 闭集 + 场景↔AppModule 映射**（本体扩展）；门户人物首页接入六面（孪生总览/人物画像/记忆/回放/本体孪生）。**学科登顶**作为"知识学院"场景内的**子视图**保留。
3. **第三步（B 的底座，按需）**：把 twin 提升为平台域，多端消费；人本体泛化（学生→所有人）；场景↔模块由本体声明。

**每次只转一个开关**：先把"入口"做对（登录→人物→世界→模块），再谈"融合"。

## 5. 必须你拍板的 5 个点（决定选型）

1. **人本体的范围**：孪生只服务"学生"，还是**所有登录人**（教师/商家/组织成员都有孪生）？（决定 B 是否必要）
2. **"世界"是几层**：**人本世界（生活场景=模块入口）** 与 **模块内部世界（如学科版图）** 是两层；确认这个"双层世界"口径？
3. **学科登顶的归属**：确认**留在智学慧眼模块内**（作为知识学院场景的子视图），**不**上移门户？
4. **"表现方式"的期望**：原型是 **2D/SVG**；"虚拟世界的表现方式实现各模块功能"——**接受 2D（与原型一致、成本可控）**，还是要 **3D/游戏化**（成本量级不同，且 uni-app 编译产物需各端重写）？
5. **门户工作台的去留**：现有"模块卡工作台"是**并入世界场景**，还是**保留为"目录"视图**（与世界并列）？

## 6. 风险与"挑毛病"（先说清，免得返工）

- **uni-app 是编译产物，运行时不能加载模块**：任何"每模块一个 3D 场景"的设想 = 每端重写，**成本极高**。建议世界=**入口/外壳**，模块功能仍是各自页面（或各自模块内的轻量场景）。
- **孪生状态跨模块需统一真源**：现在 `twin.event` 是学生域；泛化后要防止"谁的孪生、谁的宇宙"边界混乱（人本体锚点 `entity_id → public.users` 已有，可延用）。
- **权限不放松**：场景入口仍走 `app-module` 角色可见性 + 用户选用；孪生只读不越权；`assertSiteOperator/assertRole` 不变。
- **本体先行**：任何世界/场景/行动/关系的结构变更，**先改 `*.ontology.yaml` → codegen → 迁移**（禁手写结构 DDL）——原型 DSL 已给出可直接对齐的形态。
- **不重复存储**：孪生"不重复存状态"（沿用 `student-twin` 红线）——profile 取 identity、state 取业务聚合、world 取场景/版图、events 取 `twin.event`、memories 取 `agent.memory`。
