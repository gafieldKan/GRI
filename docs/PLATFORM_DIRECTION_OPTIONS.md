## 一、总评：想法"方向对、三处需纠正、一处未言明前提"

你的四条想法里，**SSO 门户**和**维度作为主数据**是**对且成熟**的；**"模块挂维度"**和**"插件"**用词**混了概念**；还有一个**你没说、但决定全局的前提**（多租户）。逐条：

### ✅ 成熟、直接可做
- **SSO + 注册**：项目已有 `auth-center`（RS256 JWT）+ `@gri/auth-client`（三端共享会话）。**不用新建，接上即可**。
- **区域/行业作骨架维度**：已完成（`ontology.region` 7999 / `ontology.industry` 832）。标准分类法作主数据是行业惯例。

### ⚠️ 我建议**否决/纠正**的三处

**① "把各模块都挂接到这两个维度下" —— 范畴错误（我最想否决的点）**
- Region/industry 是**分类维度（reference taxonomy）**，描述"**事物属于哪个区域/行业**"，不是"**模块的父级**"。
- 「组织管理台」「AI 辅导」与 ISIC 行业**没有自然归属**；强行给每个模块指定行业/区域 = 人为造关系，反而让维度失真。
- **纠正**：维度应挂到**业务对象**上（商家/订单/学校/组织/餐厅都带 `region_id` + `industry_id`）；**模块至多"可选声明作用域"**（如"某插件只在某行业可用"），且默认不挂。

**② "根据权限可选插件" —— "授权"与"选用"是两回事**
- **授权（RBAC）**＝安全边界，服务端强制，不可选。
- **选用（opt-in）**＝UX 偏好，用户 pin/隐藏，纯前端记忆。
- 你的表述把两者揉在一起。最佳实践是**解耦**：先用 RBAC 决定"你能用哪些"，再让用户"从能用的里挑想看的"。
- 且"登录授权人"是谁？**用户自助** / **管理员审批** / **角色自动**——三种模型差别很大，需你定。

**③ "插件" —— 与当前前端技术栈错配**
- 前端是 **uni-app 编译产物**（`uni build`），**运行时无法加载代码**。
- 你说的"插件"，本架构能做到的是 **注册表驱动 + 权限门禁的"应用目录"**；**真"运行时插件"需微前端**（Module Federation/qiankun）——大工程。**期望要对齐**（见方案 3）。

### ❓ 你没说、但决定全局的前提：**多租户**

"授权人按维度选模块"隐含 **区域×行业 = 运营单元/租户** 的 SaaS 模型。但实测：**业务表零 tenant 作用域**。
→ **要不要做多租户？** 这决定架构分岔（方案 1 vs 方案 2）。**这是必须先拍的板。**

### 🔧 其他不成熟处
- **AI 维护"标准分类法"有治理风险**：直接编辑 UN ISIC/M49 会**破坏其权威性**（与源版本漂移）。最佳实践是**权威源同步 + 本地覆盖分层 + HITL 审批**，而非自由编辑。
- **组合爆炸**：8000 区域 × 832 行业 的模块挂接 = 不可维护。须限粒度。
- **首页放 8000 节点树 = UX 负担**：消费者订餐不关心 ISIC。维度应是**上下文筛选器**（在相关模块内），非全体用户首页主导航。

## 三、3 个完整方案

> 三个方案**共用**：① SSO（auth-center）② 区域/行业维度（已有）③ 变更审计。差异在**"模块与维度/权限的关系模型"**与**前端形态**。

### 方案 1「务实门户」—— SSO 应用目录 + 维度作数据分类轴 ★推荐

**一句话**：门户 = SSO 登录后按权限渲染的**应用目录**；区域/行业是**业务对象**的分类轴；模块**可选**声明作用域。

| 维度 | 设计 |
|---|---|
| **首页** | `/` = 未登录→登录/注册；已登录→应用目录（卡片由 `AppModule` 注册表按 RBAC 渲染）+ 用户 pin/hide |
| **权限** | 系统角色（consumer/student/merchant/operator）× 组织角色；**授权**（服务端强制）与**选用**（前端偏好）解耦 |
| **维度** | 业务对象（restaurant/order/organization）加 `region_id` + `industry_id`（FK）；模块经 `module_region/industry` **可选**限定作用域 |
| **维度治理** | **权威源 import + 本地 overlay 分区** + operator CRUD + **HITL** + 审计；AI 命令走提案→确认 |
| **前端** | 注册表驱动导航，**不引入微前端**（沿用 uni-app 各端，门户只做入口+目录） |
| **多租户** | **暂不做**；但数据模型**预留 `tenant_id`** 以便演进 |
| **工作量/风险/价值** | **M / 低 / 高** |

**为什么推荐**：拿到你 80% 的诉求（SSO 门户 + 注册表插件 + 双维度 + 可维护），成本/风险最低，且**不阻塞**未来演进到方案 2。

---

### 方案 2「多租户运营平台」—— 区域×行业 = 租户/运营单元

**一句话**：把 **region×industry 定义为租户（运营单元）**；每个租户由 tenant-admin **启用模块 + 配置**；数据按租户隔离。

| 维度 | 设计 |
|---|---|
| **首页** | 登录后先"选/进租户（区域+行业）"，再在租户内看到其启用的模块 |
| **权限** | 三层：平台 operator → **租户 admin** → 终端用户；模块启停由租户 admin 控制 |
| **维度** | 维度**升格为租户实体**；`tenant(region, industry)` 表；业务数据全部加 `tenant_id` 作用域 |
| **维度治理** | 同方案 1，外加"开租户/关租户"生命周期 |
| **前端** | 同方案 1（可后续再上微前端） |
| **多租户** | **核心**：需全量数据作用域改造（当前 0 基础，**大改**） |
| **工作量/风险/价值** | **L / 中高 / 高**（若业务=多地多行业独立运营） |

**最贴近你字面想法**（模块挂维度），但代价是**引入完整多租户**。适合"平台要在很多区域/行业各自运营"的真实业务。

---

### 方案 3「微前端插件市场」—— 真插件运行时 + 插件 SDK

**一句话**：门户**动态加载插件**（微前端），第三方/独立团队可开发上架，形成插件生态。

| 维度 | 设计 |
|---|---|
| **首页** | 门户 = 插件宿主（qiankun/Module Federation），运行时按需加载插件包 |
| **权限** | 插件声明 **scope 化权限**（装插件=授精确权限，仿 Shopify） |
| **维度** | 同方案 1/2 的维度模型 |
| **治理** | 插件版本/契约/沙箱/上架审核（新增一整套） |
| **前端** | **引入微前端基建**（构建、沙箱、契约、版本） |
| **工作量/风险/价值** | **XL / 高 / 取决于是否有第三方生态** |

**建议暂缓（YAGNI）**：除非确有第三方开发者或独立团队要并行发版，否则投入产出比差。

## 五、我的推荐与建议路径

**推荐：方案 1 起步，朝方案 2 演进，方案 3 延后。**

1. **现在做方案 1**（SSO 应用目录 + 维度作数据轴 + HITL 治理）——低成本拿高价值。
2. **数据模型预留 `tenant_id`**：方案 1 的业务对象分类表中预留租户位，未来切方案 2 时**不改业务代码**。
3. **等有"多地多行业独立运营"的真实业务时**，再上方案 2 的多租户。
4. **方案 3 仅当出现第三方开发者**再评估。
